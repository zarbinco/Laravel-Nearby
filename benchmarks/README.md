# Proximity Query Benchmarks

This optional utility compares the exact Haversine SQL without a geographic prefilter against SQL generated by the current Eloquent proximity scopes. It checks that both queries return identical ordered record IDs before accepting each timing sample.

Run it on a dedicated development MySQL 8.4 server while other database workloads are quiet. Results depend on hardware, buffer-pool size, data distribution, selected columns, application conditions, and the optimizer's chosen plan. They are measurements of these fixtures, rather than predictions for every application.

## Setup

Install the package's development dependencies with `composer install` and enable PDO MySQL. Create a dedicated database whose name ends in `_benchmark`, such as `nearby_benchmark`, and grant the benchmark user permission to create, index, analyze, truncate, and drop tables there. The utility does not create databases or modify existing tables.

Set `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, and `DB_PASSWORD` in your shell. Keep credentials outside tracked files. `DB_PORT` defaults to 3306, and an empty password is permitted for an isolated local server. The database-name check and explicit `--run` flag are additional safeguards; they do not make a production server an appropriate benchmark target.

Each run creates a uniquely named ordinary InnoDB table and removes it in a `finally` block. Ordinary tables allow realistic persistent statistics and `ANALYZE TABLE` behavior. A forcibly terminated process can leave its generated table behind; the table name appears in the JSON output so you can remove that specific table afterward.

## Running Measurements

Without `--run`, the script shows help and does not connect to MySQL:

```bash
php benchmarks/benchmark.php --help
```

Start with 1,000 records:

```bash
php benchmarks/benchmark.php --run --output=build/benchmark-small.json
```

The default run tests both distributions, all six index layouts, and all eight operations. It takes two untimed warm-ups and five measured samples per query. Timings include native statement preparation, SQL execution, and fetching all selected rows; builder compilation, model hydration, result hashing, seeding, index changes, and plan collection are excluded. Query variants alternate execution order to reduce a consistent cache-order advantage. The report includes every sample and its median, minimum, and maximum.

Larger datasets require an explicit size option. This command captures JSON and tree plans and also runs `EXPLAIN ANALYZE`, which executes every explained query:

```bash
php benchmarks/benchmark.php --run --sizes=1000,10000,100000 --warmups=2 --repetitions=5 --plans=both --analyze --output=build/benchmark-large.json
```

Use a new `.json` output path for each run; existing files are not overwritten. The ignored `build/` directory is a suitable destination. Reports contain generated coordinates, numerical bindings, SQL, plans, environment versions, and MySQL memory settings, but no connection credentials. A report with `completed: false` is a partial run and should not be treated as a complete comparison.

## Fixtures and Queries

Data generation uses a local deterministic integer generator with seed 104729 and does not change PHP's global random state. Dataset fingerprints let you confirm repeated runs used identical data:

- **Uniform:** points are uniform on the spherical surface, with uniform longitude and inverse-sine distributed latitude.
- **Clustered:** 80% of points form a Gaussian cluster around latitude 35.6892, longitude 51.3890, with a latitude standard deviation of 0.6 degrees and longitude adjusted for latitude; the remainder is uniform on the globe.

Both datasets include twenty tenant IDs and an approximately 75% active-record share. The clustered fixture makes large-radius queries match a large fraction of rows; small uniform datasets may legitimately have no matches for a narrow radius.

| Operation | Query |
| --- | --- |
| `distance_all` | Select every ID and its distance, ordered by ID |
| `radius_small` | Within 5 km, ordered by ID |
| `radius_medium` | Within 100 km, ordered by ID |
| `radius_large` | Within 10,000 km, ordered by ID |
| `nearest_unbounded` | Nearest ten, with distance and an ID tie-breaker |
| `nearest_bounded` | Nearest ten within 250 km |
| `distance_band` | Between 25 and 100 km, inclusive |
| `application_filter` | Within 100 km, tenant 3, active records only |

The baseline reuses the library's exact SQL expression and parameter bindings without adding a box. It measures the effect of candidate filtering, rather than claiming to reproduce every PHP preparation cost of an older checkout. Unbounded operations provide a useful control because no geographic prefilter can safely impose a hidden radius.

Every fixture has an ID primary key. Index layouts add no secondary index, latitude, longitude, latitude/longitude, longitude/latitude, or tenant/active/latitude/longitude. Only the generated benchmark table is altered. `ANALYZE TABLE` refreshes statistics after each index change. These index choices are comparisons, not installation requirements or universal recommendations.

## Inspecting Plans

The default `--plans=json` stores MySQL's full estimated JSON plan for each query. Use `--plans=tree`, `--plans=both`, or `--plans=none` as needed. Inspect table access type, `possible_keys`, selected `key`, used key parts, estimated rows, filtering, and sort or temporary-table operations. Composite indexes with two range predicates do not necessarily use both columns to narrow the index scan.

Add `--analyze` to collect actual iterator timings, row counts, and loops as tree text. It adds database work outside the timed samples. Compare estimates with actual rows and the returned-row count; an estimated cost is not an elapsed time, and a limit on returned rows does not guarantee few distance evaluations.

To investigate expression reuse separately, add `--investigate-alias`. For nearest queries, this measures an additional variant ordering by the selected distance alias while preserving ID ties. It is an experiment confined to the benchmark; the utility does not modify the package's query implementation. Shorter SQL alone is insufficient evidence that MySQL performs less calculation.

You can restrict a run while investigating one plan:

```bash
php benchmarks/benchmark.php --run --sizes=100000 --distributions=clustered --indexes=none,latitude,application_first --operations=radius_medium,application_filter,nearest_unbounded --investigate-alias --plans=both --output=build/benchmark-focused.json
```

Keep performance measurements separate from correctness tests and normal CI. Repeat important comparisons on your own representative data and workload before changing application indexes.

## Profiling Version Validation

The optional guard profiler isolates PHP query-compilation overhead on the same MySQL connection:

```bash
php benchmarks/profile-guard.php --run --iterations=5000 --repetitions=7 --output=build/guard-profile.json
```

It compares four legacy per-expression validation callbacks with the current query guard for fresh builders and cloned builders sharing a query family. It reads the real PDO server-version attribute, counts those reads, warms up each variant, alternates batch order, and reports median microseconds per compilation. Queries are compiled without execution, so it creates no tables and sends no benchmark SQL. Connection setup is excluded from timing.

This is a small PHP overhead comparison, not a measurement of SQL execution latency. Fewer version-attribute reads do not imply an equivalent reduction in database query time. Use the main benchmark to assess actual query execution.
